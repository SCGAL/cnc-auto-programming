# 数控自动编程工具集（CNC Auto-Programming Toolkit）

> 两个递进的独立项目：**从"读矢量图"到"看图纸"**
>
> | | 输入 | 输出 | 自验证结果 |
> |---|---|---|---|
> | **① DXF → G 代码** | DXF 矢量图（LINE / ARC / LWPOLYLINE / CIRCLE） | 车削 G 代码 | 契约校验 **9/9** |
> | **② 图像 → G 代码** | 位图（PNG / JPG，零件轮廓图） | 车削 G 代码 | DoD 门槛子集 **56/72（77.8%）**，报错 **0** |
>
> 两者共享同一条输出链路 —— ② 复用 ① 中已被验证的 G 代码生成器，把风险隔离在"图像 → 几何"这一段。
> 语言 / 依赖：Python 3.11 + NumPy + Pillow（**图像算法全部自研，不依赖 OpenCV**）
>
> 📄 **第三方视角的完整项目介绍 → [`项目介绍.md`](项目介绍.md)**
> （面向第一次接触本项目的人，无需看源码即可读懂；全部数字标注数据源与复现命令）

## 一、项目 ①：DXF → 车削 G 代码

`dxf_to_gcode_v2.py`

### 做了什么
解析 DXF 图纸，提取直线、圆弧、LWPOLYLINE（含 bulge 圆弧）与整圆几何，做轮廓串联排序后输出车削 G 代码：
G00/G01/G02/G03 插补、半径/直径编程、绝对/增量坐标、脉冲当量量化、安全退刀、可选程序头（G18 / G54 / T / S / M03）。

### 关键过程：一次系统性缺陷排查
原始版本（`dxf_to_gcode.py`，保留作对照）"能跑通但从未被验证"。用**契约校验**逐项体检后，定位并修复 **10 类缺陷**，其中 3 类会导致机床误动作或撞刀：

| 缺陷 | 实测证据 |
|---|---|
| **bulge 圆弧圆心算到弦的另一侧** → 输出 **270° 大圆弧** | 真值圆心 `(-10,20)`，程序输出 `(0,10)` |
| **Z 镜像后未反转圆弧旋向** → 圆弧绕长边切削 | R5 圆角包角实测 270°（应 90°） |
| **I/K 按游标而非圆弧起点计算** → 圆心错位 | 起点到圆心 46.10 mm，而标注半径 R3 |
| **G91 模式只改头部注释**，坐标仍是绝对值 | 增量累加末端 (510,130) vs 绝对 (80,10) |
| **脉冲当量从未参与量化** | `--pulse 0.1` 输出 `Z30.123` |
| **快速定位不抬刀** → 实机撞刀 | `G00 Z80 X10`，而工件最大半径 20 |
| 同 Z 位置合成冗余端面线段（来回空切两遍） | 6 条有效线段输出 8 段 |
| 弧长统计一律按劣弧，与实际输出矛盾 | 输出 270° 弧，统计按 90° 弧算 |
| 文档声明 `--safe-z` 但从未实现 | — |
| DXF `$INSUNITS` 被完全忽略 | — |

### 自验证
`tests/run_checks.py` —— 对输出的 G 代码做 **9 项契约断言**：圆弧圆心正确性、旋向/包角（**用实际切削弧中点与真值比对**，这是唯一能抓住"方向反了、走了 270° 大弧"的检查）、脉冲量化合规、重复段检测、安全退刀、增量一致性。

```
修复前 1/9 通过  →  修复后 9/9 通过
```

## 二、项目 ②：图像识别 → 车削 G 代码

`image_to_gcode/`

### 做了什么
输入一张零件轮廓图，自动输出车削精加工轮廓路径的 G 代码。完整流水线：

```
图像 → 二值化(Otsu) → 去噪/形态学 → 倾斜校正(投影直方图能量 + 三角核分箱)
     → 轮廓跟踪(Moore) → 骨架细化(Zhang-Suen) → 亚像素精化
     → 区域生长分段 → 直线/圆弧判别 → 圆拟合(Kåsa 初值 + RANSAC + Gauss-Newton 精修)
     → 标定(像素→毫米) → 几何吸附(角度/共线/端点/切点求交) → 连续性检查 → G 代码
```

> 注：倾斜角估计用**投影直方图能量最大化**而非 PCA（PCA 受凹肩/倒角影响偏差 > 0.5°）；
> 分段用**区域生长 + 逐点模型选择**而非 Douglas-Peucker（DP 会把 90° 圆弧切成 4 段弦，
> 实测圆弧识别率为 0，DP 仅保留为可选 `--segment-method dp`）。
> 吸附必须在标定**之后**（吸附容差以 mm 给出）。

**约 3300 行自研图像与几何算法**（核心包 `i2g/` 3054 行 + `cli.py` 228 行），
另有约 2800 行测试代码；**零 OpenCV 依赖**（cv2 仅作可选对照，缺失时全流程可运行；
本机实测环境 cv2 即未安装，全部测试与矩阵均在此条件下跑出）。

### 关键过程：先写验证，再写算法
- 先用**合成真值测试框架**：光栅化已知几何生成带真值的测试图，覆盖
  分辨率 × 线宽 × 倾斜角 × 噪声 × 圆角半径 **五维参数矩阵**
- 全矩阵 324 例 / DoD 门槛子集 72 例，6 项精度指标自动比对
- 报告全部数字由脚本现算、可逐例追溯

### 实测精度

| 口径 | 结果 |
|---|---|
| **良态工况**（10 px/mm、线宽 2 px、无倾斜无噪声、R5） | 端点 **0.052** / 圆心 **0.069** / 半径 **0.047** / 豪斯多夫 **0.035** mm —— 目标余量 **2.9~8.5 倍** |
| **DoD 门槛子集**（72 例：px ≥ 10 且噪声 = 0） | **56 例全指标达标（77.8%）**，**报错 0** |
| 单指标独立达标率 | 圆心 / 半径 / 豪斯多夫 / 圆弧召回 **全部 100%**；端点误差 56/72（77.8%） |

> **端点误差是唯一约束项。** 未通过的 16 例全部因端点误差判定失败，且端点误差一旦通过，其余五项必然通过 —— 也就是说，整个项目的剩余差距可以收敛到一个词：**"在哪里分段"**，而不是"看不清"。

### 已知失效模式（如实报告）
`fillet_r = 15`（大圆角，与肩面相切）是当前主要失效维度。根因已定位并给出量化解释：

> 切点附近"多算一截肩面"对残差几乎无感 —— R = 150 px 的圆弧吃掉 12 px 肩面，残差只涨 `12²/(2×150) = 0.48 px`，与骨架噪声同量级。因此**基于残差的边界精修在切点处是平的**，找不到最优边界。

一条独立佐证：**端点误差在 10 px/mm 处出现平台**，不再随分辨率提升而改善 —— 证明瓶颈是结构性的边界定位误差，不是采样密度不足。

### 独立代码评审
交付前做过一次独立代码评审（只看代码、不参与实现），提出 **11 项问题、全部修复**，
另记录 **4 项未修**留待后续版本。其中四项都属于"测试全绿但实际是错的"：
- 圆弧配对无距离上限 → 两条同半径圆弧**圆心互换后指标仍全绿**（错配 8.57 mm）
- 无匹配圆弧时 `center_err`/`radius_err` 返回 0.0 → **空集拿满分**
- 端点 X 有系统性抬升 0.14 mm（占预算 70%）→ 修复后 0.141 → 0.038 mm
- 缺 Z 单调性检查 → 折返轮廓可静默输出"把零件切两遍"的程序

> 完整报告（失败分析、参数探针、评审记录、数据可追溯性）：[`image_to_gcode/精度验证报告.md`](image_to_gcode/精度验证报告.md)

## 三、快速开始

```bat
:: —— 项目①：DXF → G 代码 ——
cd tests
python make_test_dxf.py                                  :: 生成测试件
python ..\dxf_to_gcode_v2.py shaft.dxf --turning --check  :: 转换 + 自校验报告
python run_checks.py --dir out_v2 --ik fanuc --label v2   :: 9 项契约校验

:: —— 项目②：图像 → G 代码 ——
cd ..\image_to_gcode
python cli.py part.png --ref-diameter 40 --turning -o out.nc
python cli.py part.png --turning --check --viz out\viz -o out.nc   :: 附自校验与中间过程图
python run_tests.py                                       :: 单元测试（96 passed / 1 xfailed）
python -m tests.run_matrix --subset dod                   :: 精度矩阵（72 例）
python -m tests.make_report                               :: 重新生成精度报告
```

**项目② 的 CLI 用法**

```bat
:: 已知外径标定（最常用）
python cli.py part.png --ref-diameter 40 --turning -o out.nc

:: 已知像素比例
python cli.py part.png --mm-per-px 0.1 --turning -o out.nc

:: 两特征点标定
python cli.py part.png --ref-points 120,300 640,300 --ref-mm 52 --turning -o out.nc

:: 实心填充轮廓图
python cli.py part.png --ink fill --ref-diameter 40 --turning -o out.nc
```

> ⚠️ 无标定参数时程序**强制报错退出**，绝不默认假设 1 px = 1 mm。

## 五、边界（明确不做）

| 不做 | 说明 |
|---|---|
| 粗车复合循环 G71/G70 | 真实生产必需，属下一层次 |
| 螺纹 / 切槽 / 钻孔 / 端面循环 | — |
| 内孔轮廓 / 多刀具 / 刀补 G41/G42 | — |
| 装配图 / 剖视图 / 多视图识别 | 只支持单张图、单一视图、一条连续外轮廓 |
| 尺寸公差 / 形位公差（GD&T）识别 | — |
| 剖面线 / 尺寸线 / 文字的**自动**剔除 | 要求干净输入（或人工 ROI） |
| 照片透视校正 | 后续版本 |
| 刀具干涉 / 过切仿真 | — |
| **真机实测 / 与具体控制器联调** | ⚠️ **从未上过机床** |

项目② 的 CLI 强制要求显式给出 `--turning` 才会执行，就是对这条边界的确认动作。

## 六、诚实声明（重要）

1. **两个项目都未上机实测。** 全部验证是几何与代码规范层面的契约级校验，没有真机或仿真器验证。
2. **项目② 的验收目标（DoD）尚未全数达成**：56/72（77.8%）。剩余未达标项集中在"大圆角 × 倾斜"组合。
3. **I/K 轴对应与圆弧旋向依赖控制器与刀架**：按 Fanuc G18 标准实现，广数 / 新代 / 西门子各有差异；前置刀架与后置刀架的 G02/G03 需互换 —— 必须在目标机床手册上核对。
4. **这是学习性工程项目，不是 Mastercam 的替代品。** 定位是理解并打通"图纸 → 几何 → 加工程序"这条链路。
