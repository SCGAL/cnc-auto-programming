# 数控自动编程工具集

**把图纸变成数控车床能执行的程序。**

仓库里有两个递进的项目：

- **DXF → G 代码**：读矢量图纸（DXF 文件），输出车削加工程序。
- **图片 → G 代码**：读位图（PNG / JPG 的零件轮廓图），输出车削加工程序。

第二个比第一个难得多。矢量图纸里的坐标是精确给定的，程序只需要正确理解；而图片里
没有坐标，程序必须从像素中**测量**——在 10 px/mm 的图上，1 个像素就等于 0.1 mm，
测量误差会直接变成加工误差。两个项目共用同一条输出链路：图片版直接调用矢量版里
已经验证过的 G 代码生成器，把自己要负责的范围压缩到"图像 → 几何"这一段。

技术上只用 Python 3.11 + NumPy + Pillow（核心实现 4096 行，测试代码 3403 行）。
二值化、骨架细化、连通域、圆弧拟合、RANSAC 这些图像算法全部由自己实现，
**不依赖 OpenCV**。此项目的目的就是搞清楚这些算法本身怎么工作，
直接调用 `cv2.findContours` 会跳过最核心的部分。

## 现状

| | 输入 | 输出 | 实测结果 |
|---|---|---|---|
| 项目一 | DXF 矢量图 | 车削 G 代码 | 契约校验 **9/9** 通过 |
| 项目二 | 位图（PNG / JPG） | 车削 G 代码 | 验收标准 **56/72（77.8%）** 全项达标，报错 0 |

项目二的验收标准是：**在 10 px/mm 的图上，直线端点误差与圆弧圆心、半径误差 ≤ 0.2 mm，
圆弧识别率 ≥ 90%**。这个目标**还没有完全达到**，缺口集中在大半径圆角、极细笔画和带倾斜
的组合上。不过四项指标（圆弧识别率、圆心误差、半径误差、轮廓豪斯多夫距离）已经在
全部 72 例上 **100% 达标**，剩余问题收敛到一件事：*在哪里把轮廓切开成直线段和圆弧段*。

良态工况（10 px/mm、线宽 2 px、无倾斜无噪声、R5 圆角）下，六项指标都有数倍余量：

| 指标 | 目标 | 实测 | 余量 |
|---|---|---|---|
| 直线端点误差 | ≤ 0.2 mm | 0.052 mm | 3.9 倍 |
| 圆弧圆心误差 | ≤ 0.2 mm | 0.069 mm | 2.9 倍 |
| 圆弧半径误差 | ≤ 0.2 mm | 0.047 mm | 4.3 倍 |
| 类型判别正确率 | ≥ 90% | 100% | — |
| 圆弧识别率 | ≥ 90% | 100% | — |
| 轮廓豪斯多夫距离 | ≤ 0.30 mm | 0.035 mm | 8.5 倍 |

72 例逐例明细、失败原因分析、精度与分辨率的关系，见
[`image_to_gcode/精度验证报告.md`](image_to_gcode/精度验证报告.md)。

## 每个数字均可复现

图片版的做法是**先写验证框架，再写算法**。真值由程序自定义，再光栅化成图片，
于是"真值 → 图片 → 流水线 → 结果"整条链路都在框架里，误差能精确到毫米。
框架本身也要先自证，把真值喂回比对框架必须得到零误差。这条自检后来抓到过一次**测试集自身的失真**（合成图用了硬二值化，丢掉抗锯齿信息，让骨架产生+2.4 像素的系统性半径偏差），否则那个问题会被当成算法缺陷。

项目一补上一套校验之后，9 个校验只通过1 个，顺查出 10 类缺陷，其中 3 类如果真上机床会撞刀，修复后校验变成 9/9。
《精度验证报告》里的数字全部由脚本从实测 JSON 现算，无手工填写；项目二 README
里的数字由测试与 JSON 逐位比对。

> 完整项目叙述（流水线每一环在做什么、与最初计划的 11 处偏离、验证方法论、
> 完整测试结果）见 [`项目介绍.md`](项目介绍.md)。
> 两次排查的原始记录见 [`程序检查报告.md`](程序检查报告.md)。

## 快速开始

### 项目二：图片 → G 代码

```bat
cd image_to_gcode

:: 已知外径标定（最常用）
python cli.py part.png --ref-diameter 40 --turning -o out.nc

:: 已知像素比例
python cli.py part.png --mm-per-px 0.1 --turning -o out.nc

:: 用两个已知距离的特征点标定
python cli.py part.png --ref-points 120,300 640,300 --ref-mm 52 --turning -o out.nc

:: 输出中间过程图和自校验报告
python cli.py part.png --ref-diameter 40 --turning -o out.nc --viz out\viz --check --report out\report.txt
```

**没有标定参数时程序会直接报错退出**，并打印它提取到的轮廓像素包围盒供你推算比例。
它绝不默认假设 1 像素 = 1 毫米。一个尺寸整体差几倍的加工程序，比一个报错的程序危险得多。

```bat
:: 测试与精度复现
python run_tests.py                                   :: 单元测试与回归（96 passed / 1 xfailed）
python run_tests.py -m slow                            :: 含验收门槛子集（72 例）
python -m tests.run_matrix --subset dod                :: 验收门槛子集（72 例）
python -m tests.run_matrix --subset full               :: 全矩阵（324 例）
python -m tests.make_report                            :: 重新生成精度验证报告
```

### 项目一：DXF → G 代码

```bat
cd tests
python make_test_dxf.py                                     :: 生成测试图纸
python ..\dxf_to_gcode_v2.py shaft.dxf --turning --check     :: 转换并输出自校验报告
python run_checks.py --dir out_v2 --ik fanuc --label v2      :: 9 项契约校验
```

### 退出码

| 码 | 含义 |
|---|---|
| 0 | 成功 |
| 2 | 业务错误——缺少标定参数、识别到的实体数为 0、轮廓不闭合、图片读不出来。**明确报错，不静默输出垃圾** |
| 1 | 未预期的异常，附完整调用栈 |

这个工具**目前只做**：车削件上半部外轮廓的精加工轮廓路径。图片版的命令行强制要求
显式给出 `--turning` 才会执行，这就是对这条边界的确认动作。

| 不做 | 说明 |
|---|---|
| 粗车复合循环 G71/G70 | 真实生产必需，但属于下一个层次 |
| 螺纹、切槽、钻孔、端面循环 | — |
| 内孔轮廓、多刀具、刀补 G41/G42 | — |
| 装配图、剖视图、多视图识别 | 只支持单张图、单一视图、一条连续外轮廓 |
| 尺寸公差与形位公差（GD&T）识别 | — |
| 剖面线、尺寸线、文字的自动剔除 | 要求输入干净，或用 ROI 框选 |
| 照片透视校正 | 后续版本 |
| 刀具干涉与过切仿真 | — |
| 与真机联调、适配具体控制器型号 | 见下方 |

## 说明

1. **两个项目都没有上过机床。** 全部验证是几何与代码规范层面的校验，
   本项目专注于编程与工程辅助中的学习，未实机验证。
2. **项目二的验收标准还没有完全达到**：72 例中 56 例全项达标（77.8%）。
3. **I/K 轴对应关系与圆弧旋向依赖控制器和刀架。** 这里按 Fanuc G18 标准实现，
   广数、新代、西门子的约定各有差异；**前置刀架与后置刀架的 G02/G03 需要互换**。
   上机前须在目标机床的手册上核对。
4. **程序输出的 .nc 文件是 UTF-8 编码（无 BOM）、带中文注释。** 老式控制器或按 GBK
   解析注释的系统可能出现乱码，建议先在目标机床上确认注释显示正常。
5. **`--ink fill`（实心填充图）模式明显弱于线框模式**：端点误差约 1.0 mm。该模式靠
   Moore 边界跟踪取区域边界，没有线框模式的逐点亚像素精化。
6. **这是学习性质的项目，不是 Mastercam 的替代品。** 目标是理解并打通
   "图纸 → 几何 → 加工程序"这条链路。
