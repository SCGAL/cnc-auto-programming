# 数控自动编程工具集

**把图纸变成数控车床能执行的程序。**

仓库里有两个递进的项目，它们解决同一个问题的两个层次：

- **DXF → G 代码**：读矢量图纸（DXF 文件），输出车削加工程序。
- **图片 → G 代码**：读位图（PNG / JPG 的零件轮廓图），输出车削加工程序。

第二个比第一个难得多。矢量图纸里的坐标是精确的，程序只需要正确理解它；而一张图片里
没有坐标，程序必须从像素中**测量**出坐标——1 个像素在 10 px/mm 的图里就等于 0.1 mm，
测量误差会直接变成加工误差。

两个项目共用同一条输出链路：图片版直接调用矢量版里已经验证过的 G 代码生成器，
把自己要负责的范围压缩到"图像 → 几何"这一段。

技术上只用 Python 3.11 + NumPy + Pillow，核心实现 4096 行，测试代码 3403 行。
二值化、骨架细化、连通域、圆弧拟合、RANSAC 这些图像算法全部是自己实现的，
**不依赖 OpenCV**。原因很简单：这个项目的目的就是搞清楚这些算法本身怎么工作，
直接调用 `cv2.findContours` 会跳过最核心的部分。

## 现在是什么水平

不绕弯子，先说结论。

| | 输入 | 输出 | 实测结果 |
|---|---|---|---|
| 项目一 | DXF 矢量图 | 车削 G 代码 | 契约校验 **9/9** 通过 |
| 项目二 | 位图（PNG / JPG） | 车削 G 代码 | 验收标准 **56/72（77.8%）** 全项达标，报错 0 |

项目二的验收标准是：**在 10 px/mm 的图上，直线端点误差与圆弧圆心、半径误差 ≤ 0.2 mm，
圆弧识别率 ≥ 90%**。这个目标**还没有完全达到**，缺口集中在大半径圆角、极细笔画和
带倾斜的组合上。问题出在哪里、为什么，下面会讲清楚。

## 项目一：从 DXF 图纸生成车削 G 代码

### 它做什么

解析 DXF 图纸里的直线、圆弧、多段线（含 bulge 表示的圆弧）和整圆，把散落的图元
串成一条连续轮廓，再输出车削 G 代码：G00/G01/G02/G03 插补、半径或直径编程、
绝对或增量坐标、脉冲当量量化、安全退刀，以及可选的程序头（G18 平面选择、G54 工件坐标、
刀具号、主轴转速、主轴启动）。

### 起因：程序能跑，但从来没被验证过

第一版 `dxf_to_gcode.py` 是我自己写的，写完能正常输出 G 代码，看起来没问题。

后来我决定先别急着往下做，而是**写一个校验器去逐项检查它的输出**。思路是：
G 代码里每条圆弧都能从"起点坐标 + I/K 偏移量"反推出圆心，把这个圆心和 DXF 图纸里的
真值比对；圆弧的旋向和包角，则用"实际会被切削的弧中点"和真值比对——**这是唯一
能抓住"方向反了、绕了一大圈"这类错误的检查方式**，光看半径是查不出来的。

结果很不客气：**9 个断言只通过 1 个**。查下去定位到 10 类缺陷，其中 3 类如果真上机床
是会撞刀的：

| 缺陷 | 实测证据 |
|---|---|
| bulge 圆弧的圆心算到了弦的另一侧，输出 270° 大圆弧 | 真值圆心 `(-10, 20)`，程序输出 `(0, 10)` |
| Z 轴镜像后没有反转圆弧旋向，圆弧绕长边切削 | R5 圆角实测包角 270°（应为 90°） |
| I/K 按"当前游标位置"算而不是按圆弧自身起点算，圆心错位 | 起点到圆心 46.10 mm，而标注半径是 R3 |
| G91 增量模式只改了文件头的注释，坐标仍输出绝对值 | 增量累加后末端 `(510, 130)`，绝对模式是 `(80, 10)` |
| 脉冲当量参数算出了结果却从未使用 | `--pulse 0.1` 却输出 `Z30.123` |
| 快速定位时不抬高刀具，直接横向移动 | `G00 Z80 X10`，而工件最大半径是 20 |
| 自动合并同 Z 位置的垂直线段，与已有端面线重复 | 6 条有效线段输出成 8 段，刀具在同一端面空切两遍 |
| 弧长统计一律按劣弧算，与实际输出矛盾 | 实际输出 270° 弧，统计却按 90° 算 |
| 文档里声明了 `--safe-z` 参数，代码里根本没实现 | — |
| 完全忽略 DXF 的单位字段 `$INSUNITS` | 图纸若标为英寸或米，整体尺寸会差一个数量级 |

修复后的版本是 `dxf_to_gcode_v2.py`，校验从 1/9 变成 **9/9**。
原版 `dxf_to_gcode.py` 保留在仓库里作为对照。

完整的排查记录（每条缺陷的代码位置、实测证据、修复方式）见
[`程序检查报告.md`](程序检查报告.md)。

### 这件事真正的收获

缺陷本身是可以修的，修完就过去了。真正改变我做法的是另一件事：

**写程序的人和校验程序的人，看到的不是同一个东西。** 我以为程序没问题，
是因为我从来没写过能证伪它的东西。这次排查最有价值的产出不是那 10 个 bug，
而是那套校验脚本——它后来还抓住了我自己在修 bug 时引入的 2 个新缺陷。

所以第二个项目换了做法。

## 项目二：从图片生成车削 G 代码

代码在 `image_to_gcode/`，最基本的用法：

```bat
python cli.py part.png --ref-diameter 40 --turning -o out.nc
```

### 这次先写验证，再写算法

第二个项目开工前，我先把**测试框架**写完了，一行算法代码都没动。图片版没有现成的
真值可比，但可以自己造：**先用程序定义出零件的真值几何（毫米），再把它光栅化成图片**。
这样"真值 → 图片 → 流水线 → 结果"整条链路都在自己手里，任何误差都能精确定位。
真值件覆盖分辨率、线宽、倾斜角、噪声、圆角半径五个维度的组合，一共 324 例。

框架本身也要先自证，这是最容易偷懒也最致命的一步。所以我写了这样的测试：
把**真值本身**喂回比对框架，必须得到零误差；人为注入一个 0.35 mm 的平移，
必须报出 0.35 mm；两条同半径圆弧的圆心互换后，必须判为"不匹配"。

这些自证测试后来立了大功。最典型的一次：框架一直报告数字骨架有 +2.4 px 的
系统性半径偏差（算出来 R = 52.4，真值 50）。查了半天，问题**不在算法，在测试图自己**——
合成图用的是硬二值化，把抗锯齿边缘的覆盖率信息全丢了。改成抗锯齿灰度图之后偏差消失。
如果没有框架自证这一步，这个"测试集自身的失真"会被当成算法缺陷，
然后我可能真去"修"一个根本不存在的问题。

### 实测精度

**良态工况**（10 px/mm、线宽 2 px、无倾斜无噪声、R5 圆角）：

| 指标 | 目标 | 实测 | 余量 |
|---|---|---|---|
| 直线端点误差 | ≤ 0.2 mm | 0.052 mm | 3.9 倍 |
| 圆弧圆心误差 | ≤ 0.2 mm | 0.069 mm | 2.9 倍 |
| 圆弧半径误差 | ≤ 0.2 mm | 0.047 mm | 4.3 倍 |
| 类型判别正确率 | ≥ 90% | 100% | — |
| 圆弧识别率 | ≥ 90% | 100% | — |
| 轮廓豪斯多夫距离 | ≤ 0.30 mm | 0.035 mm | 8.5 倍 |

但把验收标准铺开成全部 72 种组合（10 px/mm 以上、无噪声）时，**只有 56 种六项全过**。
分开看每一项的独立达标率，问题的形状就清楚了：

| 指标 | 达标率 | 最差一例 |
|---|---|---|
| 圆弧识别率 | **100%**（72/72） | 1.000 |
| 圆弧圆心误差 | **100%**（72/72） | 0.191 mm |
| 圆弧半径误差 | **100%**（72/72） | 0.093 mm |
| 轮廓豪斯多夫距离 | **100%**（72/72） | 0.272 mm |
| 类型判别正确率 | 87.5%（63/72） | 0.889 |
| **直线端点误差** | **77.8%**（56/72） | **1.142 mm** |

四项指标已经在全部 72 例上达标。16 个失败例**全部**包含端点误差失败，
而 9 个类型判别失败的例子同时也端点失败——也就是说，**端点误差一旦通过，
其余五项必然通过**。

轮廓形状全对（豪斯多夫 100%）而端点有 22% 不达标，说明差距不在"看不清轮廓"，
而在**"在哪里把轮廓切开成直线段和圆弧段"**。整个项目的剩余问题可以收敛到这一点。

### 现在卡在哪

主要失效维度是**大半径圆角（R = 15 mm）**，通过率 58.3%，其次是**1 像素细笔画**
（62.5%）和**带倾斜的组合**（61~83%；无倾斜时 18/18 全过）。

大半径圆角难，是因为它和相邻的肩面是**相切**关系，不是相交。在切点附近，
"多算进去一截肩面"对拟合残差几乎没有影响：一个半径 150 px 的圆弧多吃掉 12 px 的肩面，
残差只涨 `12² / (2 × 150) = 0.48 px`——和骨架本身的阶梯噪声是同一量级。

**这意味着基于残差的边界精修在切点处是"平的"，找不到最优边界。** 这不是参数没调好，
而是判据在这个位置的信息量趋近于零。针对 1 像素细笔画做过的 5 组参数尝试，结果完全
相同——14 个用例都只通过 8 个。

不过"调参没用"这个说法要限定范围，否则就成了另一种失真。**更早一轮里，24 组网格探针
确实找到了改善方向**：把曲率切分容差从 0.10 收紧到 0.06、切分迭代从 1 提到 2，
验收通过率从 23/72 提到了 31/72。当时的报告里如实记了这件事——先前"这不是调参问题"
的判断**被探针推翻**了。

但 31 之后调参就推不动了。参数能改善别的地方，解决不了切点这个结构性瓶颈。

另一条独立佐证来自分辨率实验：**端点误差在 10 px/mm 处进入平台，继续提高分辨率
不再改善**（10 px/mm 是 0.052 mm，25 px/mm 还是 0.041 mm）。如果瓶颈是采样密度不足，
提高分辨率应该会变好。它没有。所以瓶颈是结构性的边界定位误差。

最近一轮我从这里找到了突破，把验收通过率从 43/72 提到 56/72，靠的是三处**机制性**修正
而不是调参。完整的提升路径是这样的：

| 改动 | 通过率 |
|---|---|
| 起点 | 23/72 |
| 收紧曲率切分容差、提高切分迭代次数（调参） | 31/72 |
| 放宽短段吸收阈值 + 加几何可行性闸门 | 41/72 |
| 回收被裁掉的子区域 | 43/72 |
| 试过一条临时放宽方案到 46/72，但含噪图端点误差从 0.167 退化到 0.608 mm | 放弃，退回 43 |
| 放宽曲率切分的搜索范围 | 50/72 |
| 弧弦比护栏 1.02 → 1.01 | 51/72 |
| 给切分加收益判据 | **56/72** |

1. **切分搜索范围。** 逐阶段打桩后发现，R15 圆角的肩面落在弧区段的最后 19 个点上，
   而旧代码的搜索上限恰好比它早 12 个点——**切分器根本看不到这个过渡**，于是一直在
   切直线段（伪切分）。把范围放宽到角度有效边界后，那一例的端点误差从 1.023 mm
   降到 0.042 mm。
2. **弧弦比护栏从 1.02 放宽到 1.01。** 切分可能把圆弧切出一段跨 30° 的碎片，
   它的"弧长/弦长"是 1.013，被 1.02 的护栏挡在"圆弧"类之外**判成了直线**，
   于是无法和同类圆弧合并回去，留下一个落在 21 mm 长弧中部的伪顶点，
   端点误差顶到 9.4 mm。
3. **给切分加了收益判据。** 只看"转角跳变够大"会切出没有建模收益的碎段。加入一个
   局部比较：切开后两段代价之和必须小于整体的 0.85 倍，否则不切。

### 一次独立代码评审

交付前我请了一个独立评审（只看代码，不参与实现）。它提出 11 项问题，已全部修复，
另有 4 项记录在案、留待后续版本。最值得说的是其中四项——它们都属于
**"测试全绿，但实际是错的"**：

| 评审发现 | 为什么危险 | 修复效果 |
|---|---|---|
| 圆弧配对没有距离上限 | 两条同半径圆角的圆心互换后，指标仍然全绿，而几何错了 8.57 mm | 加上 1.0 mm 配对上限，错配直接判为"未匹配" |
| 没有匹配到圆弧时，圆心/半径误差返回 0.0 | **空集拿满分** | 改为返回 NaN 并判失败 |
| 端点 X 有系统性抬升 | 线宽 3 px 时抬升 0.14 mm，占掉 0.2 mm 预算的 70% | 把轴线上的首末端点钉到 X=0，0.141 → 0.038 mm |
| 没有检查 Z 方向单调性 | 折返的轮廓可以静默输出"把零件切两遍"的程序 | 加入单调性检查，Z 回调超 0.2 mm 即报错 |

这四项的共同点是：**它们都不影响"程序能跑通"，只影响"数字可不可信"。**
如果没有那套自证的指标框架，这四项一个都发现不了。

## 怎么跑起来

### 项目一：DXF → G 代码

```bat
cd tests
python make_test_dxf.py                                     :: 生成测试图纸
python ..\dxf_to_gcode_v2.py shaft.dxf --turning --check     :: 转换并输出自校验报告
python run_checks.py --dir out_v2 --ik fanuc --label v2      :: 9 项契约校验

:: 常用生产参数
python ..\dxf_to_gcode_v2.py part.dxf --turning --x-diameter --header full --tool 1 --spindle 800
```

### 项目二：图片 → G 代码

```bat
cd image_to_gcode

:: 已知外径标定（最常用）
python cli.py part.png --ref-diameter 40 --turning -o out.nc

:: 已知像素比例
python cli.py part.png --mm-per-px 0.1 --turning -o out.nc

:: 用两个已知距离的特征点标定
python cli.py part.png --ref-points 120,300 640,300 --ref-mm 52 --turning -o out.nc

:: 实心填充的轮廓图（默认按线框笔画图处理）
python cli.py part.png --ink fill --ref-diameter 40 --turning -o out.nc

:: 输出中间过程图和自校验报告
python cli.py part.png --ref-diameter 40 --turning -o out.nc --viz out\viz --check --report out\report.txt
```

**没有标定参数时程序会直接报错退出**，并打印它提取到的轮廓像素包围盒供你推算比例。
它绝不默认假设 1 像素 = 1 毫米。这是刻意的：一个尺寸整体差几倍的加工程序，
比一个报错的程序危险得多。

```bat
:: 测试与精度复现
python run_tests.py                                   :: 单元测试与回归（96 passed / 1 xfailed）
python run_tests.py -m slow                            :: 含验收门槛子集（72 例）

python -m tests.run_matrix --subset quick              :: 10 例冒烟
python -m tests.run_matrix --subset dod                :: 验收门槛子集（72 例）
python -m tests.run_matrix --subset full               :: 全矩阵（324 例）
python -m tests.run_matrix --subset resolution         :: 精度与分辨率的关系
python -m tests.make_probe                            :: 参数探针
python -m tests.make_report                            :: 重新生成精度验证报告
```

### 退出码

| 码 | 含义 |
|---|---|
| 0 | 成功 |
| 2 | 业务错误——缺少标定参数、识别到的实体数为 0、轮廓不闭合、图片读不出来。**明确报错，不静默输出垃圾** |
| 1 | 未预期的异常，附完整调用栈 |

## 明确不做的事

这个工具**只做一件事**：车削件上半部外轮廓的精加工轮廓路径。图片版的命令行强制要求
显式给出 `--turning` 才会执行，这就是对这条边界的确认动作。

| 不做 | 说明 |
|---|---|
| 粗车复合循环 G71/G70 | 真实生产必需，但属于下一个层次 |
| 螺纹、切槽、钻孔、端面循环 | — |
| 内孔轮廓、多刀具、刀补 G41/G42 | — |
| 装配图、剖视图、多视图识别 | 只支持单张图、单一视图、一条连续外轮廓 |
| 尺寸公差与形位公差（GD&T）识别 | — |
| 剖面线、尺寸线、文字的自动剔除 | 要求输入干净，或用 ROI 框选 |
| 照片透视校正 | 后续版本 |
| 刀具干涉与过切仿真 | — |
| 与真机联调、适配具体控制器型号 | 见下方诚实声明 |

后续版本的想法都记在 `image_to_gcode/README.md` 的"后续版本"一节，不在当前版本实现。

## 需要说清楚的几件事

1. **两个项目都没有上过机床。** 全部验证是几何与代码规范层面的契约校验，
   没有真机，也没有仿真器验证。
2. **项目二的验收标准尚未完全达到**：72 例中 56 例全项达标（77.8%）。未达标的集中在
   "大半径圆角 × 倾斜"这一类组合，原因分析见上文和精度报告。
3. **I/K 轴对应关系与圆弧旋向依赖控制器和刀架。** 这里按 Fanuc G18 标准实现，
   广数、新代、西门子的约定各有差异；**前置刀架与后置刀架的 G02/G03 需要互换**。
   上机前必须在目标机床的手册上核对。
4. **程序输出的 .nc 文件是 UTF-8 编码（无 BOM）、带中文注释。** 老式控制器或按 GBK
   解析注释的系统可能出现乱码，建议先在目标机床上确认注释显示正常，或改用纯 ASCII 注释。
5. **`--ink fill`（实心填充图）模式明显弱于线框模式**：端点误差约 1.0 mm。该模式靠
   Moore 边界跟踪取区域边界，没有线框模式的逐点亚像素精化。这是已知的取舍。
6. **这是学习性质的项目，不是 Mastercam 的替代品。** 目标是理解并打通
   "图纸 → 几何 → 加工程序"这条链路。
